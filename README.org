#+TITLE: Datum
#+AUTHOR: Sebastian Monia & Gary Hollis
#+OPTIONS: toc:3 num:nil

An Emacs SQL IDE backed by a Python CLI.  Connect to any ODBC database,
get instant completion, goto-definition, parameter signatures, one-keystroke
table operations, and import/export -- all without leaving your editor.

Datum keeps all compute in Python and uses Emacs as a smart terminal.
Structured data flows between them via an envelope protocol that is
invisible to the user but keeps the Emacs side informed about dialect,
metadata, and introspection results.  The Python CLI is also usable
standalone from any terminal.

* Features

- Connect to any database with an ODBC driver (MSSQL, PostgreSQL, SQLite, MySQL, Oracle, ...)
- Auto-detect SQL dialect or set it explicitly
- Introspection commands: =:tables=, =:columns=, =:schemas=, =:databases=, =:routines=, =:running=
- Auto-introspect on connect: completion is populated automatically (no manual =:tables= needed)
- Export query results to CSV, Parquet, or JSON (=:out=)
- Import files into SQL tables with schema inference (=:in=)
- Custom query templates with placeholders and ODBC parameters
- Native org-mode table output: query results are valid org tables, ready to yank into any =.org= document
- Emacs integration: completion-at-point, eldoc parameter signatures, mode line status, keybindings
- Admin panels for server administration without leaving Emacs:
  - Sessions and running queries, with the full text of any of them
  - Databases: create, alter, drop; files and filegroups; backup and restore (MSSQL)
  - Schemas and tables: a column builder, and altering columns of a table that exists
  - Logins, roles and database users, with passwords treated as secrets
  - Object-level permissions: grant, deny and revoke down to a column
  - A read-only browser for the server's own filesystem
  - SQL Agent jobs, steps, schedules and history (MSSQL) — creating and
    editing jobs as well as their parts
  - Reachable from the query buffer by key as well as from the panels:
    =C-c t= for tables and schemas, =C-c d= for databases, =C-c g= for
    logins and roles
- Optional Polars backend for faster import/export (falls back to pyarrow or stdlib)

* Connecting to a database

** Using individual parameters

#+begin_src shell
datum --driver "ODBC Driver 18 for SQL Server" \
      --server myserver --database mydb \
      --user sa --pass ENV=DB_SECRET
#+end_src

** Using a DSN

#+begin_src shell
datum --dsn MyDSN
#+end_src

** Using a connection string

#+begin_src shell
datum --conn-string="Driver={PostgreSQL Unicode};Server=localhost;Database=mydb;Uid=postgres;Pwd=secret"
#+end_src

** Environment variable substitution

Any parameter value starting with =ENV== pulls from an environment variable:

#+begin_src shell
datum --driver "PostgreSQL Unicode" --server localhost \
      --user ENV=PG_USER --pass ENV=PG_PASS --database mydb
#+end_src

** Dialect detection

Datum auto-detects the SQL dialect from the driver name or DSN.  You can
override it with =--sql-type=:

#+begin_src shell
datum --dsn MyDSN --sql-type postgres
#+end_src

Supported dialects: =mssql=, =postgres=, =mysql=, =sqlite=, =oracle=, =ansi= (fallback).

* Query input

Type SQL at the =>= prompt.  Queries are sent to the server when you:

- End a line with =;;=
- Type =GO= on its own line

#+begin_example
>select * from users;;

>select *
>from orders
>where total > 100
>GO
#+end_example

** Parameterized queries

Use =?= as an ODBC parameter placeholder.  Datum prompts for each value:

#+begin_example
>select * from users where name = ? and age > ?;;
1>Alice
2>30
#+end_example

Values are properly escaped by pyodbc.

* Output format

All query results and introspection output are formatted as org-mode
tables:

#+begin_example
| id | name  | email             | created_at          |
|----+-------+-------------------+---------------------|
|  1 | Alice | alice@example.com | 2024-01-15 09:30:00 |
|  2 | Bob   | bob@example.com   | 2024-01-16 14:22:00 |

Rows printed: 2/2
#+end_example

This means every result you see -- queries, =:tables=, =:columns=,
=:running=, everything -- is a valid org table.  You can yank results
directly into any =.org= document and they align with =TAB=
immediately, no reformatting needed.

Use =C-c s w= to copy the last result to the kill ring, ready to paste.

** Export (=:out=)

Export the *next* query's results to a file.  Format is inferred from the
file extension.

#+begin_example
>:out /tmp/results.csv
:out target set to: /tmp/results.csv (will error if file exists)
Run your query now. The next query's results will be exported.

>select * from orders;;
#+end_example

Supported formats: =.csv=, =.parquet=, =.json= (newline-delimited).

When a query produces duplicate column names (e.g. =SELECT a.id, b.id
FROM ...=), they are automatically disambiguated with =_1=, =_2= suffixes,
and a warning is shown.

Use =:force= to overwrite an existing file:

#+begin_example
>:out /tmp/results.parquet :force
#+end_example

*** BCP acceleration (MSSQL)

On MSSQL, exporting tables with LOB columns (=varchar(max)=, =nvarchar(max)=)
via pyodbc can be very slow because ODBC falls back to row-by-row =SQLGetData=
for unbounded columns.  Microsoft's =bcp= utility bypasses this limitation
using the TDS bulk protocol.

To enable bcp for CSV exports, set =sql-datum-bcp= in your connection entry:

#+begin_example elisp
(my-mssql-connection
 (sql-server "myserver.example.com,1433")
 (sql-database "mydb")
 (sql-datum-bcp t)
 (sql-datum-bcp-extra ("-u")))  ;; -u = trust self-signed cert
#+end_example

The =--bcp= flag can also be passed directly on the command line.  Extra bcp
arguments (like =-u= for trusting self-signed certificates) are passed via
=--bcp-extra=.

BCP is only used when all of these conditions are met:
- =--bcp= was passed (or =sql-datum-bcp= is =t=)
- The export format is CSV
- =bcp= is on =PATH=
- The query is not parameterized

If bcp fails, datum falls back to the normal pyodbc export path automatically.

** Import (=:in=)

Import a file into a SQL table.  Schema is inferred automatically.

#+begin_example
>:in /tmp/data.csv my_table
#+end_example

Modes:

| Syntax                                   | Behavior                      |
|------------------------------------------+-------------------------------|
| =:in file table=                         | Error if table exists         |
| =:in file table :insert=                | Append to existing table      |
| =:in file table :replace=               | Drop, recreate, and insert    |
| =:in file table :batch 500=             | Custom batch size (default 1000) |

Supported formats: =.csv=, =.parquet=, =.json=.

The =:batch N= flag controls how many rows are sent per =executemany= call.
Lower values use less memory (useful for wide tables); higher values are faster.
The default is 1000.

When Polars is installed, it handles file reading and type inference.
Otherwise falls back to pyarrow (for parquet/json) or stdlib csv.

** Legacy CSV export

#+begin_example
>:csv /tmp/session_output.csv
#+end_example

Appends all subsequent query output to the file until disabled with =:csv=
(no argument).

** Script execution

#+begin_example
>:script /path/to/query.sql
#+end_example

Reads and executes a SQL file.  Supports ={placeholder}= and =?= parameters
like custom commands.

* Configuration file

Datum looks for an INI file in this order:

1. The path given by =--config=
2. =$XDG_CONFIG_HOME/datum/config.ini=
3. =~/.config/datum/config.ini=

** Example configuration

#+begin_src ini
[general]
rows_to_print=0
column_display_length=0
null_string=[NULL]
newline_replacement=[NL]
tab_replacement=[TAB]

[queries]
top=SELECT * FROM {table} LIMIT {how_many}
find=SELECT * FROM {table} WHERE {column} LIKE '%{pattern}%'
#+end_src

** Custom commands

Queries in the =[queries]= section become commands prefixed with =:=.
They support two levels of parameterization:

- ={placeholder}= -- replaced via Python string formatting (prompted interactively)
- =?= -- ODBC parameterized values (escaped by pyodbc)

#+begin_example
>:top
table>users
how_many>10

Command query:
 SELECT * FROM users LIMIT 10
#+end_example

You can combine both:

#+begin_src ini
[queries]
search=SELECT * FROM {table} WHERE {field} = ?
#+end_src

#+begin_example
>:search
field>name
table>users

Command query:
 SELECT * FROM users WHERE name = ?
1>Alice
#+end_example

** Setup

               '("my-mssql"

Then use =M-x sql-connect= and pick a connection, or =M-x sql-datum= to be

** Password handling

Three options for =sql-password=:

- A literal string (visible in =list-processes=)
- ='ask= -- prompted with =read-passwd= each time
- ='auth-source= -- looked up via Emacs =auth-source= (supports =.authinfo.gpg=, GNOME Keyring, etc.)

For =auth-source=, add an entry keyed by connection name:

#+begin_example
machine my-postgres login postgres password secret123
#+end_example

By default, passwords are passed via a temporary environment variable
(=SQLDATUMPASS=) so they don't appear in process listings.

** Connection gotchas

*** Always set all login fields explicitly

Emacs =sql-mode= stores =sql-server=, =sql-database=, =sql-user=, and
=sql-password= as global variables.  When you connect, these are set to
whatever that connection entry specifies — but fields you *omit* keep
their previous value.  This means a password from connection A can leak
into connection B if B doesn't explicitly clear it.

*Rule of thumb:* every entry in =sql-connection-alist= should set all
four fields, even if the value is an empty string.

#+begin_src emacs-lisp
;; BAD — if a previous connection set sql-password, it leaks here:
'("my-local-pg"
  (sql-product 'datum)
  (sql-server "")
  (sql-user "")
  ;; sql-password not set — inherits from last connection!
  (sql-datum-options '("--conn-string=Driver={PostgreSQL Unicode};...")))

;; GOOD — explicitly clear the password for peer/ident auth:
'("my-local-pg"
  (sql-product 'datum)
  (sql-server "")
  (sql-database "")
  (sql-user "")
  (sql-password "")
  (sql-datum-options '("--conn-string=Driver={PostgreSQL Unicode};...")))
#+end_src

This is especially important when switching between password-authenticated
connections (e.g. Docker test databases) and passwordless connections (e.g.
local PostgreSQL with peer auth).

** Scratch buffer

The scratch buffer is a convenient, fast way to write and send SQL
interactively.  =sql-datum-scratch= opens (or switches to) a
=*datum-scratch*= buffer in =sql-mode=, wired to the active datum
connection.  Unlike the SQLi REPL, a scratch buffer gives you a full
editing environment: multi-line queries, undo history, =M-.=
goto-definition, completion, and all the =C-c t= / =C-c s=
keybindings.  Use =C-c C-r= to send a region or =C-c C-b= to send the
whole buffer.

With a prefix argument (=C-u=), it creates an additional scratch buffer
with a numeric suffix -- useful for keeping separate workspaces (one for
exploration, one for DDL, one for a long analysis).

Note that all datum features -- completion, =M-.= goto-definition,
eldoc, keybindings -- work in any =sql-mode= buffer associated with a
datum connection, not just scratch buffers.  So =.sql= files work just
as well; the scratch buffer is simply a fast way to start writing SQL
without creating a file.

A typical workflow:

1. =M-x sql-connect= -- connect to a database
2. =C-c q= -- open the scratch buffer (completion is already populated)
3. Write SQL, =C-c C-c= to run region or paragraph, =M-.= to inspect objects, iterate

Bind it globally for quick access:

#+begin_src emacs-lisp
(autoload 'sql-datum-scratch "sql-datum" nil t)
(global-set-key (kbd "C-c q") #'sql-datum-scratch)
#+end_src

** Completion at point

Table, schema, column, and routine names are available for completion in
both the SQLi buffer and =sql-mode= editing buffers.  Works with
=completion-at-point= (=C-M-i=), Company, Corfu, etc.

When =sql-datum-auto-introspect= is non-nil (the default), completion data
is populated automatically on connect — no need to run =:tables= or
=:routines= manually.  You can also run =:refresh= at any time to silently
update the completion data.

*** Contextual column completion

Column completion is context-aware: when the current SQL statement
references specific tables (via =FROM=, =JOIN=, =UPDATE=, or =INTO=),
only columns from those tables are offered.  The scanner reads the full
statement -- both before and after point -- so =SELECT c<TAB> FROM
customers= correctly narrows to the =customers= columns.

Columns are fetched lazily.  When you =TAB= and the columns for a
referenced table haven't been cached yet, Datum silently sends a
=:columns= request in the background.  The first =TAB= falls back to all
known columns; the second =TAB= (once the fetch completes) shows the
narrowed contextual set.  Tables that were previously introspected with
=:columns= are used from cache immediately.

Multi-table statements work as expected: =FROM t1 JOIN t2 ON ... WHERE
<TAB>= offers columns from both =t1= and =t2=.  When no tables can be
detected (e.g. typing =SELECT <TAB>= before a =FROM= clause has been
written), completion falls back to all cached columns.

When contextual columns are available, they are sorted before tables,
schemas, and other object types in the completion list.

Qualified column completion is also supported: typing =table.<TAB>= or
=alias.<TAB>= offers =table.column= candidates with type annotations.
Table aliases are resolved automatically -- =FROM users u WHERE u.<TAB>=
shows columns from the =users= table.

*** Cross-database completion (MSSQL)

On MSSQL, completion supports three-part names (=other_db.schema.table=).
Type a database name, complete it with =TAB=, type =.=, and hit =TAB=
again -- Datum fetches that database's tables, routines, and schemas
asynchronously on demand.  The first =TAB= after a new database prefix
triggers a background fetch; press =TAB= again once the fetch completes
to see completions.  Results are cached per-session so subsequent
completions are instant.

Object names containing dots are bracket-quoted automatically (e.g.
=master.dbo.[My.Dotted.Name]=) so they display as valid three-part
references and don't get confused with additional qualifiers.

Running =C-c s f= (=sql-datum-refresh=) refreshes not only the current
database but also re-fetches any cross-database caches built during the
session, so dropped or newly created objects are picked up everywhere.

This works because MSSQL supports cross-database queries via three-part
catalog references.  PostgreSQL cannot query across databases without
reconnecting, so this feature is MSSQL-only.

You can also introspect a remote database manually with =:refresh-db <name>=.

*** Quoted identifier completion

Identifiers containing spaces, hyphens, or other special characters are
automatically quoted when completed.  Each dialect uses its native quote
style by default: double quotes for PostgreSQL (="my column"=), square
brackets for MSSQL (=[my column]=), backticks for MySQL (=`my column`=).
Only the segments that need quoting are wrapped — e.g. =public."my table"=.

Set =sql-datum-prefer-ansi-quotes= to =t= to use ANSI double-quote
quoting for all dialects instead of dialect-specific characters.

You can start typing with an opening quote, bracket, or backtick
(="che<TAB>=, =[che<TAB>=, or =`che<TAB>=) and completion will match
against the bare name, then produce the correctly quoted result without
double-quoting.

*** Schema-qualified completion

Completion supports schema-qualified names.  Both bare names (=users=) and
schema-qualified names (=dbo.users=) are available as candidates.  Typing
=dbo.= and pressing =TAB= shows all tables and routines in the =dbo= schema.

*** Routine parameter completion

For stored procedures, typing =TAB= after the procedure name offers
=@parameter= names from the routine's signature.  Parameter completion is
context-aware:

- After =@param== (an already-assigned parameter), no further parameter
  names are suggested until you type a comma
- Inside string literals (single quotes), completion is suppressed

For functions, completing a function name automatically inserts parentheses
and places the cursor between them.  Eldoc shows the function signature
in the minibuffer while you type inside the parentheses.

*** TAB setup

By default, =TAB= in =sql-mode= is bound to indentation, not completion.
To make =TAB= complete when point is mid-word (and indent otherwise), add:

#+begin_src emacs-lisp
(add-hook 'sql-mode-hook
          (lambda () (setq-local tab-always-indent 'complete)))
#+end_src

** Goto definition (=M-.=)

Press =M-.= on any SQL identifier to jump to its definition:

- *Tables*: column listing (name, type, nullability, defaults)
- *Views*: the view's SQL source
- *Functions / Procedures*: full source code

Definitions open in a read-only =sql-mode= buffer.  =M-.= keeps working
inside definition buffers, so you can drill from a view into the tables it
references, or from a procedure into functions it calls.  =M-,= pops back
through the xref marker stack; =q= also goes back one level.

With no identifier at point, =M-.= prompts for a name.

The definition command is completely silent in the SQLi buffer -- no
command echo or output appears there.  Errors (object not found, etc.)
are reported in the minibuffer.

** Mode line

The mode line shows connection status:

#+end_example

Format: =[datum:dialect:database:server:user]=

** Running queries auto-refresh

When you run =:running= (or =C-c s r=), the results open in a dedicated
buffer showing session ID, user, status, duration, and SQL text for each
running query. The output uses the same tabular format as regular query
results and respects =:chars= for column width.

| Key | Action               |
|-----+----------------------|
| =g= | Manual refresh       |
| =a= | Toggle auto-refresh  |
| =q= | Quit and stop timer  |

The buffer auto-refreshes every 5 seconds by default (customizable via
=sql-datum-running-refresh-interval=). A timestamp shows the last refresh
time. The timer stops automatically when the buffer is no longer visible.

** Admin panels (=C-c s a=)

Admin panels provide interactive views for server administration.  Press
=C-c s a= and select a panel:

- =activity=  — Active sessions and queries (MSSQL, PostgreSQL)
- =databases= — Create, alter, drop databases; manage files, backup/restore (MSSQL, PostgreSQL)
- =jobs=      — SQL Agent jobs, steps, schedules, history (MSSQL)
- =schema=    — Schemas and tables of the current database (MSSQL, PostgreSQL)
- =filesystem= — The server's own disk, read-only (MSSQL, PostgreSQL)
- =security=  — Logins, roles, database users (MSSQL, PostgreSQL)
- =ssis=      — SSIS packages (MSSQL)

Every panel names the server it is on, under its title, and carries the
connection in its buffer name — =*datum-admin:databases [prod]*=.  Both
matter once more than one connection is open: a listing or a database
list looks much the same on any machine, and without the connection in
the name every connection would share one buffer per panel, so opening
a panel on a second server would silently replace the first and a key
pressed in what looked like the first would act on the second.  The
server comes from what the connection already reported, so naming it
costs no query.

The keys available in a panel are shown in its *header line*, which stays
visible however far the contents scroll.  Panel-specific actions come
first, followed by the common keys below.  Top-level panels auto-refresh
on a timer; sub-panels do not, but re-draw themselves after any action
that changes what they show, and =g= refreshes them on demand.

| =a=            | Toggle auto-refresh                     |

*** Activity panel

Shows running sessions with SPID, user, database, status, wait type,
duration, CPU, reads/writes, blocking info, and a preview of the SQL text.

| Key   | Action                                     |
|-------+--------------------------------------------|
| =M-.= | Show full query text with session metadata |
| =M-,= | Return to the activity panel               |
| =k=   | Kill session (with confirmation)           |

=M-.= opens the complete query text in a =sql-mode= buffer with session
metadata as SQL comments (SPID, user, database, status, duration, host,
program name, etc.).  The xref marker stack is used, so =M-,= returns to
the activity panel.

*** Databases panel

Lists databases with owner, size and collation, plus recovery model on
MSSQL and encoding and session count on PostgreSQL.

| Key | Action                                   |
|-----+------------------------------------------|
| =N= | New database (wizard)                    |
| =E= | Edit settings                            |
| =F= | Manage files (MSSQL)                     |
| =K= | Backup and restore (MSSQL)               |
| =D= | Drop database (confirmation)             |

The create wizard offers what the dialect actually supports, populated
from the server: owners, collations, templates, tablespaces and
encodings are read live rather than hardcoded.

Dropping guards against the usual failure: it refuses the database you
are connected to, reports how many sessions are active, and offers a
force that ends them first (=SET SINGLE_USER= on MSSQL,
=pg_terminate_backend= on PostgreSQL, so it works before PG 13).  The
name must be retyped to confirm.

Editing applies only the settings you actually changed, so submitting an
untouched form takes no locks and says so.

**** Database files (=F=, MSSQL)

PostgreSQL manages its own storage, so this is MSSQL only; tablespaces
there are server-level rather than per-database.

| Key | Action                                    |
|-----+-------------------------------------------|
| =N= | Add a data or log file                    |
| =E= | Change size, autogrowth and max size      |
| =D= | Remove the file (emptied first)           |
| =S= | Shrink the file to a target size          |

Editing a file offers only its size limits: a file's name, path, type
and filegroup are fixed once it exists.  Removing one runs =DBCC
SHRINKFILE ... EMPTYFILE= first, since =REMOVE FILE= fails while the
file still holds pages.

**** Backup and restore (=K=, MSSQL)

PostgreSQL cannot back itself up through SQL — =pg_dump= and
=pg_basebackup= are external programs — so this is MSSQL only.

=K= on a database lists its backup history from =msdb=.

| Key | Action                     |
|-----+----------------------------|
| =N= | Back up now                |
| =R= | Restore                    |

Backups can be full, differential or log, optionally compressed,
checksummed and copy-only, and either overwrite the file or append to
it.  Paths are on the server, so the =Browse= button applies.

Restoring reads the backup's own file list and generates a =MOVE= for
every file.  Without that the restore would try to write over the paths
recorded in the backup, which belong to whichever database was backed
up.  Restoring over an existing database ends its sessions first and
returns it to multi-user afterwards; restoring into a database that does
not exist yet skips that step rather than failing on it.

Returning the database to multi-user is not part of the restore: it
happens whether the restore worked or not.  Ending the sessions is how a
restore gets exclusive access, and leaving the database shut because the
restore failed locks everybody out — worse than the failure itself, and
not obviously connected to it.  Where the reopening cannot be done
either, the error says so and gives the statement to run once whatever
is holding the database has gone.

Turning off *Bring Online* leaves the database restoring, so further log
backups can be applied; there is nothing to reopen in that case, since
=ALTER DATABASE= has nothing to say to a database that is still
restoring.

Both run on the background connection rather than the session's own.  A
backup holds its connection for as long as it takes, and the process
reads the next command on that same thread, so running it on the session
would leave the session answering nothing until the backup finished.
The form is still checked before the hand-off, so a missing field is
answered while you are still looking at the form, and a preview never
leaves the session at all — the SQL is what you are waiting to read.

*** Jobs panel

Shows SQL Agent jobs with status, enabled state, the step currently
executing, last run result and next run time.  Executing jobs sort first.

| Key | Action                                |
|-----+---------------------------------------|
| =d= | Job detail (steps + schedules)        |
| =H= | Job history                           |
| =s= | Start job                             |
| =S= | Stop job                              |
| =N= | New job                               |
| =E= | Open the job: properties, steps, schedules |
| =D= | Delete the job (confirmation)         |
| =e= | Enable/disable toggle                 |

=E= on a job *opens* it, which is where everything about it is: the
job's own properties as the first section, then its steps, then its
schedules — the way SSMS puts them on pages of one dialog rather than
down separate paths.  =d= does the same thing.

Inside, =E=, =N= and =D= act on whichever section point is in: on the
*Job* section they edit or delete the job itself, on *Steps* and
*Schedules* they edit, add and remove those.  Each opens the same
wizard form the other panels use, so they navigate the same way: arrow
keys between fields, =TAB= to complete or move on, =C-c C-c= to submit.  In the list they act on the job itself: its name,
whether it is enabled, its description, owner and category, and what it
writes to the event log, who it emails, and whether it deletes itself
once it has run — the General and Notifications pages of SSMS's job
dialog.

Steps and schedules are not on that form: they are lists rather than
properties, and the detail view already edits them.  So a new job is
made first and filled in after, with =d= and then =N=.

A new job is also given the local server to run on.  =sp_add_job= alone
leaves a job with no target server, which SQL Server accepts and then
never runs — SSMS adds it for you, and so does this.

Renaming is done by editing the name: the form remembers what the job
was called when it opened, so an edited name renames the job rather than
making a second one, and its steps, schedules and history come along.
Deleting asks first, saying how many steps, schedules and history rows
would go with it, and wants the name typed back.

*** Schema panel

Works inside whichever database the session is connected to, so =:use=
changes what it shows.  Lists the schemas of that database with their
owner and table count.

| Key | Action                        |
|-----+-------------------------------|
| =N= | New schema                    |
| =T= | Tables in this schema         |
| =D= | Drop schema (confirmation)    |

Dropping reports how many tables the schema holds.  PostgreSQL offers a
cascade that drops them too; SQL Server has none, so its objects must be
dropped or moved first, and the confirmation says so.

**** Tables (=T=)

| Key | Action                    |
|-----+---------------------------|
| =N= | New table (builder)       |
| =E= | Alter columns             |
| =D= | Drop table                |

Both are also reachable without walking the panels: =C-c t N= opens
the builder for a schema, and =C-c t E= opens the editor on the table
at point, completing the name from the introspection cache the same
way =C-c t d= and =C-c t D= do.  A bare name is resolved to its schema
automatically, and you are asked which one only when the name appears
in more than one.

The table builder takes a list of columns — name, type, nullable,
primary key and default — with =[INS]= and =[DEL]= to add and remove
rows.  Ticking primary key on more than one column produces a composite
key.

The type is a completing field rather than a menu: =TAB= narrows the
suggestions as you type and folds case, so =in= finds =INT=, and those suggestions are per dialect, so
=INT IDENTITY(1,1)= appears on MSSQL and =BIGSERIAL= on PostgreSQL.
They are suggestions only — a size none of them names, =VARCHAR(120)=
or =DECIMAL(9,3)=, is accepted just as well.

=E= on a table opens the same list, prefilled with the columns it
already has, and applies only what you change.  Adding a column, widening
a type, changing nullability or setting a default all work; the dialect
difference is handled for you, since MSSQL carries type and nullability
in one =ALTER COLUMN= while PostgreSQL needs a statement for each.

Renaming works there too.  Each row remembers what it was called when
the form opened, so editing a name in place is applied as a rename —
=sp_rename= on MSSQL, =ALTER TABLE ... RENAME COLUMN= on PostgreSQL —
and the column keeps its data.  Removing a row and inserting another is
what it looks like: the old column is dropped and a new one added.

Any change that drops a column shows the full plan and asks for the
table name to be typed before running.

A default is an expression rather than a literal, so it can be neither
quoted nor parameterised.  Only a number, a quoted string, or a bare
word optionally called as a zero-argument function — =0=, ='n/a'=,
=NULL=, =GETDATE()= — are accepted; anything else is refused rather than
interpolated.

*** Security panel

Lists server logins on MSSQL and roles on PostgreSQL.  PostgreSQL has no
separate database user: a role that can log in is already both.

| Key | Action                                        |
|-----+-----------------------------------------------|
| =N= | New login/role                                |
| =E= | Edit login/role                               |
| =D= | Drop login/role (confirmation)                |
| =U= | Database users for this login (MSSQL)         |
| =P= | Permissions held by this login or role        |

The login list includes an *Owns (dbo)* column.  Owning a database makes
a login =dbo= inside it with full control, regardless of any server
role, so a login with no server roles is not necessarily unprivileged.

Passwords are treated as secrets: the field is masked, an edit form never
sends the current password back out, and the SQL preview substitutes the
value before display.  Leaving the password blank when editing keeps the
current one.

Dropping counts the principal's live sessions first — a login holding a
connection cannot be dropped — and offers a force that ends them.

In the database-users view (=U=), =N= maps the login into a database, =E=
edits the roles it holds there, =D= removes the mapping, and =P= shows
the permissions the login holds in that database.  Roles are offered per
database, since they only exist once the database is known.

**** Object-level permissions (=P=)

The permissions view lists every permission a principal holds, one row
per permission, with the scope and the securable it applies to:

| Key | Action                                    |
|-----+-------------------------------------------|
| =G= | Grant or deny on a securable              |
| =R= | Revoke the permission on the row at point |

Where the view starts from differs by dialect, because the dialects
differ.  On MSSQL a login is a server principal, and its rights inside a
database belong to the user it maps to — so =P= on the login list shows
*server* permissions, and =U= then =P= shows what it may do in one
database.  On PostgreSQL a role is cluster-wide but privileges hang off
objects, and an object belongs to one database, so =P= shows the
connected database.  The panel title says which.

=G= asks for the scope before offering permissions, the same way editing
a user's roles asks for the database first: what can be granted depends
on it.  SELECT means something on a table, =USAGE= on a schema and
=CONNECT= on a database, and offering all of them at once would be
offering nonsense.  Scopes are database, schema, object and column —
MSSQL adds server at the login level.

The checklist then opens ticked as things already stand on the server,
and submitting reconciles the difference rather than reapplying
everything: unticking a permission revokes it, and a permission left
alone is not touched, so a grant carrying =WITH GRANT OPTION= keeps it.

MSSQL can =DENY=, which outranks any grant the principal picks up from a
role; PostgreSQL cannot, so it has no *Denied* list, and asking it to
deny is refused rather than quietly turned into a revoke.  Naming a
permission in both lists denies it.

A row whose state is =REVOKE= is not leftover noise.  Revoking one
column of a table that is granted as a whole leaves that row behind, and
it is what keeps the column out of the grant — the column is excluded
while the rest of the table stays readable.

Permission names are checked against the list for their scope rather
than quoted into the statement, so a name that is not one of them cannot
reach the server at all.  Identifiers are escaped per dialect as
everywhere else.

*** Server filesystem panel

The files a database server cares about — data files, logs, backups —
live on the *server's* filesystem, which is usually not the machine
Emacs is running on.  Both MSSQL and PostgreSQL can enumerate a
directory over SQL, so this presents that as a listing to walk through,
in the spirit of dired but read-only: nothing here writes, renames or
deletes.

| Key               | Action                                  |
|-------------------+-----------------------------------------|
| =RET= / =e= / =f= | Open the directory, or view the file    |
| =^=               | Parent directory                        |
| =v=               | View the file at point                  |
| =w=               | Copy the path at point to the kill ring |
| =s=               | Cycle the sort: name, size, date        |
| =C-u s=           | Reverse the current sort                |
| =(=               | Show names only, or the details again   |
| =g=               | Reload                                  |
| =o=               | Fetch the file and let Emacs open it    |
| =C=               | Copy what is marked here                |
| =m= / =u=         | Mark / unmark, moving on                |
| =t= / =U=         | Toggle the marks / drop them all        |

The keys are dired's where dired has one for the job, since that is
what the hands expect: =e= and =f= open, =w= copies the name, =s=
cycles the sort, =(= hides the details, =^= goes up.  =C-u s= turns the
current sort around rather than moving on, so each of the three can be
read either way; =RET= on a column header does the same for that
column, and the state is shown in the line under the title.  Two of those are
shared with other panels and change meaning with the panel — =e=
enables or disables a job elsewhere, and =s= starts one.

Directory names are shown in dired's own =dired-directory= face and the
directory line in =dired-header=, so a listing reads the way a listing
should.  It is *not* a dired buffer, though, and the mode line says
=datum-fs= rather than =Dired= to make that plain: it is read-only, it
is on another machine, and dired's editing keys are not here.

=C-c s b= opens it at the server's default data directory; with a
prefix argument it asks where to start.  The parent directory is listed
as a =..= row, so going up is visible rather than something you have to
know.

Path arithmetic stays on the server side, because the separator depends
on the server's OS and the Emacs client has no way to know it — SQL
Server runs on Linux as readily as on Windows.  Navigation therefore
uses the full path the server reported for each entry rather than one
assembled here.

**** Copying files off the server

The datum process runs beside Emacs — it is the ODBC client — so a file
read over SQL can be written straight to the local disk.  Nothing
travels through the envelope, which is the same route =:out= already
takes for exported results.

=o= fetches the file at point whole and hands it to Emacs, which then
decides what it is: an archive opens in =archive-mode=, an image in
=image-mode=, and so on.  That is the answer to viewing a zip — =v=
reads a capped prefix and decodes it as text, which no archive survives,
and its note says as much and points at =o=.

=C= copies what is marked — or what is at point — into a directory you
choose.  A directory is copied with everything under it.

Fetched files are kept under =sql-datum-download-directory=, or a
=datum-files= directory under the temporary one, named so that Emacs
still recognises them: the basename is kept, so a =.zip= still looks
like a =.zip=, and the directories above it become a hash of the server
path so two files of the same name do not collide.  A copy is reused
when its size and timestamp still match what the listing reports, which
costs nothing to check — the row already carries both.  So looking at a
file with =o= and then keeping it with =C= fetches it once.

Both are bounded by =sql-datum-download-limit=, and a directory is
measured whole against it before anything is copied, so a stray key on
a multi-gigabyte backup does not quietly start pulling it.  Within a
directory, one unreadable file is reported and the rest still arrive.

A copy runs on the background worker's own connection, not the one the
interactive session uses.  Reading a file holds its connection for as
long as the file takes, and the process reads the next command on the
same thread — so copying on the session's connection would leave the
session unable to answer anything until the file was done.  The worker
already exists for introspection, and has a connection of its own.

=v= stays on the session, since a capped peek answers at once and its
ordering is easier to follow that way.

Reads are chunked only where that helps.  SQL Server has no seek —
=OPENROWSET= starts at the beginning of the file every time — so a file
is read whole there; PostgreSQL seeks, so a large one is pulled in
pieces and never held entirely in memory.

Nothing here writes to the server.  Both dialects *can* write, as it
happens — PostgreSQL through =lo_export= and =COPY=, SQL Server through
=BACKUP= and =xp_create_subdir= — but a write through a database
connection runs as the *server's* account with its privileges, which is
a sharper edge than dired's, and is left out deliberately.

**** Windows drives

Windows has no single filesystem root: each drive is its own tree, and
=C:\= has nothing above it.  Dired has no answer to this either — on
Windows it simply stops at the top of a drive, and changing drive means
typing another path.

So the panel supplies the missing top.  Going up from =C:\= — or from a
UNC share such as =\\fileserver\backups= — lands on a list of the
server's drives, which the =..= row labels as such rather than showing a
bare marker.  Each drive is a directory row, so =RET= descends into it
the same as any other.  The list shows the free space in bytes and the
kind of drive (=DRIVE_FIXED=, =DRIVE_REMOTE=), and sorts with =o= like
any other panel.

On a server whose filesystem does have a single root, =/= is simply the
top and no drive list is offered.

This is MSSQL only.  It reads =sys.dm_os_enumerate_fixed_drives= on SQL
Server 2019 and later, falling back to =xp_fixeddrives= on older ones.
PostgreSQL has no portable way to enumerate drives, so nothing is
invented for it: on Windows a PostgreSQL server stops at the drive root.

Unlike the other panels, this one does not poll: a directory listing is
not something to watch tick over, and dired does not revert itself
either.  =g= refreshes it, and =a= turns polling on where you do want
it — watching a backup file being written, say.

The listing is of that directory only, not of what is under it, and
each row shows a bare name — the directory itself is named once in the
title, as dired does it.  Each row still carries its full path, so
navigation and =w= use the path the server reported rather than one
assembled here; =i= shows it along with the rest of the row.

Sizes are shown as plain byte counts rather than prettified, so that
sorting the column with =o= sorts numerically.

=v= reads the first 256KB into a read-only buffer.  The file is read as
bytes and decoded on this side rather than by the server, because
neither server decodes it usefully: SQL Server's =SINGLE_CLOB= reads a
byte at a time, so a UTF-16 file — which is what Windows tools write,
XML especially — arrives with a NUL after every character and renders
as though double-spaced, while =SINGLE_NCLOB= refuses a UTF-16 file
that carries no byte-order mark, and PostgreSQL's =pg_read_file=
refuses anything not valid in the server encoding.  A byte-order mark
settles the encoding where there is one, an interleaved NUL gives away
UTF-16 where there is not, and bytes that decode as nothing are shown
replaced rather than refused.

A file that does not decode as text at all — a backup, sitting in the
same directory as the logs worth reading — is named rather than dumped:
the buffer says what it is instead of filling with control characters.  The server reads as
*its own* service account rather than as you, so it reaches the files it
owns — its error log, its configuration — and is refused for anything
else, which is reported rather than raised.  On PostgreSQL, listing a
directory needs superuser or membership of =pg_read_server_files=; a
plain role gets a permission error from =pg_ls_dir=.

* Envelope protocol

Datum communicates structured data to Emacs via envelope lines:

#+begin_example
##DATUM:type:payload##
#+end_example

These are stripped from the visible buffer by a =comint-preoutput-filter= and
acted on silently.

| Type          | Payload              | Purpose                           |
|---------------+----------------------+-----------------------------------|
| =info=        | message              | Status message in minibuffer      |
| =warn=        | message              | Warning in minibuffer             |
| =error=       | message              | Error in minibuffer               |
| =dialect=     | mssql/postgres/mysql/sqlite/oracle/ansi | Set SQL dialect                   |
| =meta=        | key:value            | Metadata (server, database, etc.) |
| =result-file=  | path:format          | Exported file notification        |
| =definition=   | JSON {"name":...,"text":...} | DDL/source for goto-definition    |
| =introspect=   | kind:json-array      | Introspection data (replace)      |
| =introspect+=  | kind:json-array      | Introspection data (append chunk) |
| =running-text= | formatted-text       | Running queries display           |
